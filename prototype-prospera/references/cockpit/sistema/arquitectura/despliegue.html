🗺️ Diagrama de despliegue — ecosistema Cockpit

Antes que funcionalidades: qué corre dónde, qué datos viven dónde, cómo se comunican los nodos. Modelo Fabricante / Organización / Edge (CK-18). El Fabricante construye y distribuye (no razona en runtime); la Organización instala y opera con sus datos en su red; el Edge son apps sobre Claude Code local.  ·  Clic en cualquier nodo para su ficha (de NODOS.md, SSoT). Base 2026-07-08 (CK-18): método entregado en arneses (deroga límite IP) · N6 = Repositorio Oficial confidencial (ya no GitHub) · nacen N15/N16/N17/N18/N19 · mueren N1/N4/N7.
Principio rector (CK-18 + CK-21): el sistema es una fábrica de software que construye el Organization Twin de cada cliente y lo opera como instancia aislada. Plano del Fabricante = nuestro (construye, versiona, firma y distribuye — no toca datos del cliente). Plano de la Organización = del cliente, single-tenant, en DOS modalidades (D3): hosteada por nosotros (default — instancia aislada, cifrada, bajo DPA, exportable: "tu organización as-code es un repo git que te llevas cuando quieras") o en su red (tier enterprise/regulados). Misma arquitectura; la instancia no sabe dónde corre. Edge = apps sobre Claude Code local (una mecánica, arneses por puesto). El flujo ES el twin: el Repositorio Oficial (N6) declara el estado DESEADO → el Lakehouse (N16) observa el estado REAL → Cockpit (N13) mide el hilo de oro (objetivos→OKR→KPI) y sostiene la BRECHA CONTINUA: brecha→proyecto→KPI movido [R17] — GitOps organizacional, el loop nunca cierra. El método se entrega empaquetado en arneses (Arnesia licenciada); la protección pasa de arquitectura a licencia + contrato. "Transitan, no persisten" = promesa del tier en-red-del-cliente (chequeo 2); en el default hosteado la promesa es la instancia aislada + exportable.

✅ Decisiones de arquitectura (CK-18)

Firmadas (operador, CK-18 — D1..D5)

  1. Deroga el límite de IP "el método nunca al cliente" (D1). El método se entrega empaquetado en arneses; Arnesia se entrega al cliente para que los mantenga. Protección = licencia + contrato (canal N3 revocable), ya no arquitectura.
  2. Mueren N1, N4, N7. El Motor de Discovery server-side (N1) renace como arneses en N2/N14; la voz (N4) se difiere; los agentes efímeros (N7) mueren — todo el levantamiento es vía consultor (Consultio sobre Claude Code).
  3. N6 = Repositorio Oficial confidencial en la infra del cliente (ya no GitHub): git self-hosted (Forgejo); BD = índice derivado, nunca SSoT.
  4. Nacen Arnesia (N15), Data Lakehouse (N16), Colab Studio (N17), sistemas de la org (N18), Analista de Calidad (N19); N18/N19 como nodos propios (D2).
  5. Data Lakehouse (D3, CK-18): superseded por CK-21 (ver abajo). Knowledge DB (D5): declarada pendiente, files-first en el repo cuando haya demanda.
  6. Consultio (D4) = nombre de la App del Consultor (linaje DevStudio).

Firmadas (operador, CK-21 — el pivote twin, 2026-07-16/17)

  1. Organization as Code → Organization Twin (D1/D2): twin = deseado (N6) × real (N16) × brecha continua (N13); diferenciador = hilo de oro medido + ciclo brecha→proyecto→KPI movido [R17].
  2. Default comercial invertido (D3): instancia single-tenant hosteada por nosotros (DPA, cifrada, exportable); en la red del cliente = tier enterprise/regulados; multitenant = fase 2. Misma arquitectura en ambas.
  3. N3 asciende a Portal (D4): puerta comercial [R16] — login/cobro/asientos, licencias por fingerprint compuesto, NO MAC — además del canal técnico [R9].
  4. Consultio v0 (D7): los arneses del método sobre Claude Code pelado, sin app shell — ya no espera al clon DevStudio (llega en F3).
  5. Gestión de Cambios al MVP (D5/D8): el pipeline dev→UAT→prod ES la gestión de cambios ISO.
  6. Frontera métricas de persona (CK-24): el twin mide roles/procesos/áreas; vista persona-nombrada = opt-in Gobernanza + consentimiento.
